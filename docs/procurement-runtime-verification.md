# 采购补件等待与运行入口验证

验证日期为 2026-11-15。本阶段使用受控事件和时钟，未额外发送邮件。

## 运行行为

采购邮箱的 main 启动 IMAP 轮询及同进程的维护线程。维护线程每秒调用 materialize_due_followups，
只检查已明确成功发送、未结束、仍属当前申请版本的补件等待。
到期后生成待确认草稿，重复检查通过 application_id、version、kind 唯一约束去重。
真正发信仍只从负责人确认后的处理路径发生。
IMAP 等待网络响应期间，到期检查可继续运行。程序退出时通知维护线程停止并等待它结束。

邮件入站和草稿发送领取各自在 SQLite 写事务内完成。
回复先提交则取消旧草稿，旧页面领取失败；领取先完成则承认该次发送可能在途，
保留其结果并标记原等待结束，不再因原截止时间重复催办。
等待结束使用独立 closed_at，原 sent_at 和 due_at 保留。
未包含新增字段的真实回复也建立新申请版本，重复事件仍由 Message-ID 去重。

## 八项受控验证

1. A 等补件时 B 可完成审批，两个并发到期检查只生成一份 A 的催办草稿。
2. 回复先提交、旧草稿随后领取时，领取失败；重启后旧草稿仍撤销，原截止时间保留。
3. 领取先完成、回复随后提交时，记录在途发送结果并结束原等待，无第二份原催办。
4. 从真实 main 入口启动，模拟 IMAP 进程在运行，不打开页面也能生成已到期草稿。
5. 明确发送失败不启动等待。
6. 发送结果未知不启动等待。
7. 旧 followups 表升级后保留截止时间，并在到期后正常产生草稿。
8. 两个运行角色同时打开旧数据库时，列迁移串行完成，原等待不丢失。

并发顺序用事件控制，避免把随机调度结果当作证明。到期场景使用受控时间值；
