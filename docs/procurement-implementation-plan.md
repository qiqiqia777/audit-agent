## 待解决的实现差距

1. 采购入口直接调用规则函数。自然语言解析主要是标签和正则，制度条文写在函数里，案例在邮箱存储层查询。采购场景尚未使用 MiniHermes 的模型循环与工具调用。
2. 明确发送失败和结果未知可显示，但缺少单独补发、人工核实及完整尝试记录。决定与发送之间的进程退出需要恢复路径。
3. 催办以打开详情时检查到期。补件回复与发送草稿之间的并发、已回复但材料未变化、审批结束后的草稿状态等仍需验收。
4. 发送草稿先认领再联网。必须定义回复先到和发送先认领的顺序，并保证该顺序可测试、可恢复。
5. SMTP 适配器用 NOOP 的响应作回执；拒收字典抛 RuntimeError 与页面的异常分类不一致。需按实际发送阶段记录已知结果与未知结果，保存 Message-ID 及尝试证据。
6. 页面只显示最近一次材料差异和有限结果，完整申请版本、入站原文、补件与通知历史待补齐。
7. 现有 CI 的离线测试会发现 evals 下的邮箱测试，但 Ruff 路径未包含 email_agent。全新安装、打包和从真实运行入口验证需纳入交付。

以上是源码审视发现的缺口，尚未实跑的并发场景作为风险和待验证项。

## 按依赖执行

### 第一步，建立可靠的申请与通知状态

统一 SQLite 中的申请版本、入站事件、负责人决定、补件等待、草稿和发送尝试记录。
每次补件等待使用独立标识，决定与发信尝试分别持久化。金额使用分或精确十进制表示。
认领、决定、归属和版本校验在事务中完成，并记录决定者和对应材料版本。
保留现有申请，按现有表增量迁移。

验收包括旧数据库升级、重复事件、进程在各发送阶段退出、两个请求同时点击和旧版本审批。
失败不得产生新的审批决定。没有可验证的投递结果时进入待核实状态。

### 第二步，接入真实 MiniHermes 审查

复用 minihermes.loop.agent.run_loop、ToolRegistry 和既有模型适配，建立仅用于采购的工具集合。
工具提供版本化演示制度、当前申请材料和负责人获准查看的本部门已办结同类案例。
从后端身份绑定部门和申请，模型输入无法扩大授权范围。
一次审查输出材料建议、缺项、制度版本与条款编号、案例编号和草稿，保存所据申请版本。
后端校验输出结构、引用真实性、金额口径和必填字段。超时、无效结构、未知条款和迭代上限均保留待核实原因。
模型审查在待处理任务中运行，A 等待模型或补件时 B 仍可处理；结果只写回对应版本。

验收包括自然语言的两类申请、相同金额两种计费口径、同类历史获批但本次缺用途、恶意邮件索取其他部门案例，以及审查期间材料更新。
离线用脚本化模型响应验证工具与权限；另用真实模型运行虚构样例并记录提供商、模型、输入版本和工具引用结果。
不能用离线假响应代替真实模型验收。

### 第三步，完成软件补件与版本审批

负责人预览模型起草的补件请求，点击后发送；员工以原邮件会话或申请编号回复。
关联同时核对发件人，使用发送记录中的 Message-ID 和 References。无法唯一归属则展示候选申请，人工选择前所有候选均保持原值。
保留每封原邮件、版本变更、制度与建议快照。页面明确显示材料和总额差异，提交时绑定所查看的申请版本和通知内容。

验收运行 5 席、12 个月、120 元/月的原需求示例，分别得到 7200 和 1440 元。
再将 5 席改为 8 席，旧表单不得决定或发信，新页面展示 7200→11520。
通过页面验证跨部门列表、详情、审批、候选分配和案例原记录的拒绝路径。
用真实测试邮箱验证补件请求、原会话回复和最终通知。完成这些证据后关闭 #3。

### 第四步，完成催办、撤销和通知恢复

补件请求成功提交 SMTP 后开始等待，默认 48 小时，演示配置 60 秒。
到期检查由邮箱运行入口处理，重复检查仅生成一份待确认催办。恢复后沿用原等待时间。
以已接收事件及发送认领的事务顺序处理回复与催办竞争；先到的回复必须阻止旧草稿发送。
对材料未变化的回复也结束当前等待，仍有缺项时形成下一轮补件草稿。
明确失败允许负责人预览后单独补发；结果未知先由负责人登记核实结果，再决定补发或确认送达。
重试只影响发送尝试，保留原决定。保存每次尝试的时间、目标、内容版本、Message-ID 与结果。

验收覆盖 A 等待而 B 办结、重启续办、到期去重、回复撤销、重复点击、回复与发送并发、明确拒收、连接中断及决定后退出。

### 第五步，完成演示与交付

统一页面的待办、建议与出处、补件草稿、版本差异、审批历史、发送记录和需核实项。
用真实浏览器和测试账户走完 PRD 六段现场流程，双部门使用虚构员工，实际外发继续限于授权的自发自收地址。
从干净检出安装并运行收信和 Web 服务，验证重启、样例名册、配置和数据库迁移步骤。
交付架构与数据状态说明、部署说明、测试报告和可复演脚本。
测试报告按需求逐项链接代码、离线断言、真实模型或真实邮件证据、浏览器记录及剩余限制。
完成全部范围才关闭 #4 并完成连续目标。

## PR 与验证约定

每一步可按能独立验收的业务切片提交 PR，复用现有 Issue，不以测试数量作为完成标准。
本地运行变更相关测试和项目要求的全量离线回归；GitHub CI 必须验证 PR 最新提交。
现有模型依赖和适配按环境配置核实，不在计划中固定尚未验证可用的模型。
CI、权限和合并规则的改动按已确认规则留给用户审阅。常规业务 PR 在验收证据齐全且 CI 成功后按既有授权合并。
按上述依赖顺序推进。整体仍以 PRD 三周、84 小时的投入目标为背景，当前证据不足以承诺精确剩余工时。
