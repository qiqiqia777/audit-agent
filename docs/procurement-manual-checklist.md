# 手动浏览器验收

用户选择稍后手动验证浏览器交互。本入口使用虚构员工、固定采购资料、规则审查和本地演示收件箱；
真实 MiniHermes 与真实邮箱证据见 [阶段报告](procurement-model-verification.md)。
页面顶部明确标注演示模式，所有修改均写入独立演示数据库。

## 启动

在 audit-agent 仓库根目录完成开发依赖安装后运行：

```powershell
python scripts/procurement_demo.py
```

打开 http://127.0.0.1:8092/ 。测试账号 design 属于设计部，sales 属于销售部，两者密码均为 demo-only。
默认数据在 data/procurement-acceptance/manual-demo，重启保留操作结果。
如需重新开始一轮，用 --directory 指定新的独立目录，例如 data/procurement-acceptance/manual-demo-2。
程序会拒绝混用没有演示标记的现有数据库。

## 检查清单

下面是待人工确认项，HTTP 自动化通过不代表这些浏览器操作已经完成。

1. 用 design 登录，应看到本部门的演示设备、报价含糊的软件、两个待分配软件样例和本部门历史案例。
   打开「演示软件」，应显示费用口径缺失，历史参考里有「设计部历史出图」，没有销售部历史。
   材料版本和入站原文能展开查看。
2. 在演示控制区将「下一次发送」设为明确拒收，打开设备申请，预览通知并点击批准。
   应同时看到已批准与通知发送失败，决定人与时间保留。
   切回成功后补发，演示收件箱里应只有当前申请的结果，发送记录保留前一次失败。
3. 软件申请点击「发送补件请求」。等待至少 60 秒后刷新，应出现一条待确认催办，反复刷新也只有一条。
   在顶部控制区填写该申请编号，提交「每席位每月120元」。
   应出现 7200 元并撤销旧催办；旧草稿不能再发送。
4. 保留 7200 元页面标签页，另开同一申请页面，在控制区提交「改成8席」。
   回到旧标签页点击批准应被拒绝，且演示收件箱没有结果通知。
   新页面显示 5→8 席、7200→11520 元，确认新版后才生成批准通知。
5. 测试归属歧义时，在控制区留空申请编号，提交「改成8席」。
   应列出待分配候选，选择前候选材料保持原值。通过候选详情核对后选定一份，只有该申请改变。
6. 用 sales 登录，复制 design 申请详情地址直接访问应被拒绝。
   销售部演示收件箱不能显示设计部通知；切回 design 可继续查看自己的历史。
7. 在一个尚未决定的申请上将发送结果设为连接中断，再执行决定。
   应显示结果待核实，并要求填写核实依据。确认未送达后，切回成功再补发。
   原决定保持不变，核实人与依据可回看。此演示中的未知结果实际没有放入本地收件箱。

如果上一轮已处理了所需申请，可在新演示目录重跑。不要用已决定的申请验证第二次审批。
验收完成后，在聊天中报告通过项或具体失败步骤及页面显示内容，助手据此记录最终浏览器证据。
停止演示可在运行命令的终端按 Ctrl+C。
